# 1. Introduction

## 1.1 Purpose

Stage 3F introduces the complete lifecycle management mechanism for PulseQueue worker processes.

The purpose is to ensure that workers can start, operate, respond to operating-system termination signals, stop accepting new jobs, finish or safely interrupt in-flight execution, and release resources.

This phase completes the initial background worker engine milestone.

## 1.2 Current System

Previous phases provide:

- PostgreSQL persistence.
- Atomic job claiming.
- Worker ownership and claim tokens.
- Lease management and renewal.
- Worker configuration.
- Handler registry.
- Job execution engine.
- Panic recovery.
- Ownership-checked completion and failure.
- Continuous polling.
- Queue subscriptions.
- Context cancellation.
- Temporary database error handling.

The remaining requirement is to coordinate the complete worker lifecycle.

## 1.3 Objectives

1. Implement signal-aware worker lifecycle management.
2. Handle `SIGINT` and `SIGTERM`.
3. Stop accepting new jobs when shutdown begins.
4. Allow in-flight jobs to finish within a configurable grace period.
5. Continue lease renewal during graceful execution.
6. Cancel execution when the shutdown timeout expires.
7. Handle interrupted jobs without incorrectly recording successful completion or ordinary handler failure.
8. Close PostgreSQL connections and other resources safely.
9. Prevent resource cleanup while worker operations are still active.
10. Add lifecycle and integration tests.

## 1.4 Out of Scope

- Multiple concurrent jobs per worker.
- Distributed shutdown coordination.
- Forced termination of arbitrary Go handler functions.
- Guaranteed exactly-once execution.
- Automatic retry policies.
- Kubernetes orchestration.
- Worker autoscaling.

These are separate concerns or future improvements.

## 2.2 Lifecycle States

The worker should have a clearly defined lifecycle.

| State | Description |
|---|---|
| Starting | Initializing configuration and dependencies |
| Running | Accepting and processing jobs |
| Stopping | Shutdown requested; no new jobs accepted |
| Draining | Waiting for in-flight execution |
| Cancelling | Grace period expired; execution cancellation requested |

The lifecycle manager should prevent invalid transitions.

# 3. Signal Handling

## 3.1 Supported Signals

The worker should handle:

- `SIGINT`: commonly generated by Ctrl+C.
- `SIGTERM`: commonly sent by process managers and container orchestrators.

Use Go's `os/signal` package.

Example:

```go
signalCtx, stop := signal.NotifyContext(
    context.Background(),
    os.Interrupt,
    syscall.SIGTERM,
)
defer stop()
```

The signal context indicates that shutdown has been requested.

It should not automatically be used as the context for an in-flight handler if the desired behavior is to let that handler finish gracefully.

## 3.2 Signal Responsibilities

When a termination signal arrives:

1. Detect the signal.
2. Initiate shutdown exactly once.
3. Stop new job claiming.
4. Start the shutdown grace period.
5. Wait for active execution.
6. Cancel execution if the grace period expires.
7. Release resources after worker operations have stopped.

Do not immediately terminate the process when the first signal arrives.

## 3.3 Second Signal

A second termination signal may indicate that the operator wants the process to exit more urgently.

V1 may use the default signal behavior after the signal notification is stopped.

However, the worker must not assume that all cleanup will finish after a second signal.

Document that a forced termination can interrupt in-flight work and leave its lease to expire.

# 4. Graceful Shutdown

## 4.1 Purpose

Graceful shutdown allows the worker to finish its current job before exiting.

The worker must stop claiming new jobs as soon as shutdown begins.

## 4.2 Shutdown Timeout

Reuse the existing configuration:

```go
ShutdownTimeout time.Duration
```

Example:

```text
Shutdown timeout: 30 seconds

Shutdown requested: 10:00:00
Deadline:            10:00:30
```

If the job completes before the deadline, the worker shuts down normally.

If the deadline expires, the execution context is cancelled.

## 4.3 Stop Claiming New Jobs

The polling loop must stop before another claim begins.

This requires a clear distinction between:

- The context used to stop polling.
- The context used to control active job execution.

A single cancelled context must not unintentionally cancel the handler immediately when graceful draining is intended.

## 4.4 Separate Polling and Execution Cancellation

The lifecycle design must support two related but different cancellation events.

**Polling cancellation:**

- Prevents new claims.
- Stops empty-queue waits.
- Interrupts claim operations where possible.

**Execution cancellation:**

- Cancels the active handler when the grace period expires.
- Stops lease renewal after execution is no longer safe to continue.
- Must not happen merely because shutdown was requested.

The poller and executor contracts may need to be adjusted to support this separation.

A useful conceptual model is:

```text
Lifecycle Manager
       |
       +---- Polling Context
       |          |
       |          +---- Stop immediately
       |
       +---- Execution Context
                  |
                  +---- Continue during grace period
                  |
                  +---- Cancel on timeout
```

Avoid using `context.WithoutCancel` as a complete shutdown solution without an explicit deadline and cancellation mechanism.

# 5. In-flight Job Handling

## 5.1 Normal Completion

If a handler completes within the grace period:

1. The handler returns.
2. Lease renewal stops.
3. The executor verifies current ownership.
4. The result is persisted.
5. The executor returns.
6. The worker proceeds to resource cleanup.

The job must not be interrupted simply because the worker is shutting down.

## 5.2 Shutdown Timeout

If the grace period expires:

1. Cancel the execution context.
2. Ask the handler to stop cooperatively.
3. Stop lease renewal after the execution has been interrupted.
4. Do not report successful completion unless it was confirmed.
5. Do not release ownership while the handler may still be executing.
6. Allow the lease to expire if safe ownership recovery cannot be established.

## 5.3 Interrupted Execution Is Not an Ordinary Failure

An important distinction must be made between:

- A handler returning a business or processing error.
- A handler being interrupted because the worker is shutting down.

A shutdown cancellation should not automatically become an ordinary failed job.

The executor needs a defined interruption outcome.

Recommended V1 behavior:

- If the handler cooperatively returns because its execution context was cancelled, classify the outcome as interrupted.
- Do not mark it completed.
- Do not automatically mark it failed.
- Do not perform an unconditional ownership release.
- Stop renewal once execution has stopped.
- Allow the lease recovery mechanism to handle the abandoned running job later.

This behavior depends on the recovery policy introduced in the reliability phase.

If a handler ignores context cancellation, Go cannot forcibly terminate it. The process may eventually be terminated by the operating system, and the job may require lease recovery.

## 5.4 External Side Effects

Cancellation does not undo external operations.

For example, a handler may have sent an email immediately before cancellation.

The job may eventually be executed again.

Handlers must therefore use idempotency mechanisms wherever possible.

# 6. Lease Renewal During Shutdown

## 6.1 Continue Renewal During Graceful Draining

Lease renewal must continue while an in-flight handler is still executing.

Otherwise, the job could be reclaimed by another worker before the current handler finishes.

## 6.2 Stop Renewal After Execution Ends

The renewal loop must be stopped and joined before final result persistence and resource cleanup.

The executor should guarantee that its renewal goroutine cannot continue using the database pool after the executor has returned.

## 6.3 Timeout Behavior

When execution is cancelled because the grace period expires:

- Stop renewal after the handler has actually stopped, where possible.
- Do not clear ownership merely to make the job available sooner.
- Let the lease expire if the handler's state is uncertain.
- Avoid closing the database pool while renewal or persistence operations are still active.

A handler that ignores context cancellation creates an important limitation: the process cannot safely assume that its execution has stopped.

# 7. Resource Management

## 7.1 Resources

The worker may own:

- PostgreSQL connection pool.
- Logger resources.
- Metrics exporters.
- External service clients.
- Background goroutines.
- Signal notification registrations.

Each resource must have a defined cleanup responsibility.

## 7.2 Cleanup Order

Recommended shutdown order:

1. Stop accepting new jobs.
2. Drain or interrupt active execution.
3. Stop lease renewal.
4. Wait for worker goroutines to finish.
5. Close external service clients where appropriate.
6. Flush logging or telemetry resources.
7. Close the PostgreSQL connection pool.
8. Return from the worker process.

The database pool must not be closed while an active executor operation may still need it.

## 7.3 Cleanup Error Handling

Resource cleanup should continue even when an earlier cleanup operation returns an error.

Collect and report cleanup errors.

Use the project's existing error handling conventions.

Do not silently ignore important cleanup failures.

# 8. Worker Lifecycle Manager

## 8.1 Purpose

The lifecycle manager coordinates the complete startup and shutdown process.

It should not duplicate job execution or repository behavior.

## 8.2 Suggested Structure

An illustrative structure:

```go
type Lifecycle struct {
    poller          Runner
    shutdownTimeout time.Duration
    logger          *slog.Logger
}
```

The lifecycle manager may also receive resource cleanup callbacks or use a higher-level application composition structure.

Keep the design proportional to the actual number of resources.

## 8.3 Run Contract

A possible lifecycle contract:

```go
type Lifecycle interface {
    Run(ctx context.Context) error
}
```

The exact API should follow the existing worker package conventions.

The lifecycle manager should:

1. Start the worker.
2. Observe shutdown requests.
3. Stop polling.
4. Wait for in-flight execution.
5. Apply the shutdown deadline.
6. Release resources.
7. Return meaningful errors.

# 9. Worker Bootstrap

## 9.1 Purpose

The worker entry point should be responsible for composing dependencies and starting the lifecycle manager.

Recommended file:

```text
cmd/worker/main.go
```

## 9.2 Startup Sequence

1. Load shared application configuration.
2. Load worker configuration.
3. Initialize logger.
4. Initialize PostgreSQL connection pool.
5. Verify database readiness.
6. Create handler registry.
7. Register application handlers.
8. Create executor.
9. Create poller.
10. Create lifecycle manager.
11. Register signal handling.
12. Run the worker lifecycle.

## 9.3 Shutdown Sequence

When the lifecycle manager returns:

1. Ensure all worker operations have stopped.
2. Run resource cleanup.
3. Close the database pool.
4. Flush logging resources.
5. Return the final process result.

Avoid calling `log.Fatal` before deferred cleanup has completed, because it calls `os.Exit` and skips deferred functions.

Prefer returning errors to a top-level process function and handling the exit status after cleanup.

# 10. Testing Strategy

## 10.1 Signal Handling Tests

Test:

- SIGINT initiates shutdown.
- SIGTERM initiates shutdown.
- Shutdown is initiated only once.
- A second signal follows the documented forced-shutdown policy.

Prefer testing signal-independent lifecycle logic with contexts and controlled channels. OS signal integration tests should be isolated and deterministic.

## 10.2 Polling Tests

Verify:

- No new claims occur after shutdown begins.
- Empty queue waiting stops.
- An in-progress claim is interrupted safely.
- Polling exits cleanly.

## 10.3 In-flight Execution Tests

Verify:

- A job can finish during the grace period.
- Lease renewal continues during draining.
- Successful completion is persisted.
- Execution is cancelled when the grace period expires.
- Shutdown cancellation is not incorrectly persisted as ordinary handler failure.
- Ownership is not unconditionally released.
- Stale workers cannot overwrite job state.

## 10.4 Resource Cleanup Tests

Verify:

- Cleanup happens after worker operations stop.
- Database pool closes exactly once.
- Cleanup continues after an earlier cleanup error.
- Renewal goroutines do not access a closed pool.
- Logging and telemetry resources are flushed.

## 10.5 Integration Tests

Run a worker against real PostgreSQL.

Test:

1. Start the worker.
2. Create a pending job.
3. Verify it is executed.
4. Request graceful shutdown.
5. Verify the final job state.
6. Verify the process stops.
7. Verify the database pool is closed.

Also test a job that exceeds the configured shutdown timeout.

# 14. Risks and Technical Considerations

## 14.1 Cooperative Cancellation

Go does not provide a safe mechanism to forcibly stop an arbitrary running goroutine.

Handlers must respect context cancellation.

A handler that ignores cancellation may continue executing after the grace period.

## 14.2 Uncertain External Side Effects

A cancelled handler may already have completed an external operation.

The job must be treated as potentially executable again.

Idempotency is therefore essential.

## 14.3 Lease Expiration

The lease must remain valid while a handler is draining.

After forced interruption, the worker must not continue renewing indefinitely.

Recovery must be coordinated with the future abandoned-job recovery mechanism.

## 14.4 Database Pool Closure

Closing the database pool too early may interrupt completion, lease renewal or failure persistence.

Resource cleanup must happen only after active database-dependent operations have stopped.

## 14.5 Shutdown Timeout

The configured timeout is a grace period, not a guarantee that every handler can be forcibly terminated within that period.

The process manager may eventually terminate the process if the handler does not cooperate.

# 16. Final Summary

Stage 3F completes the initial PulseQueue worker-engine lifecycle.

It provides signal handling, graceful draining, shutdown timeouts, execution cancellation and safe resource cleanup.

The most important design principle is to distinguish stopping new work from cancelling existing work.

A graceful shutdown first prevents new jobs from being claimed, then allows the current job to finish within a bounded period.

If the timeout expires, the worker cancels execution cooperatively and preserves ownership safety rather than pretending that an uncertain job has completed or failed.

**Stage 3F outcome:** A lifecycle-managed Go worker process capable of starting, processing jobs, responding to termination signals, draining active work and releasing resources safely.

## 17. Implementation Status

The Stage 3F lifecycle is implemented with separate polling and execution
cancellation contexts:

- `Worker.RunGraceful` stops claiming when its parent context is cancelled.
- An active handler continues running during `ShutdownTimeout`.
- Lease renewal continues while the handler drains.
- A timeout cancels the handler cooperatively and does not persist a
  completion or ordinary failure result.
- Completion and ordinary handler failures during the grace period use a
  non-cancelled persistence context so an already-finished job can be recorded.
- The worker bootstrap closes the PostgreSQL pool only after the worker runner
  returns.
- The first `SIGINT` or `SIGTERM` starts graceful shutdown. Signal
  notification is then stopped, so a second signal uses the operating system's
  default termination behavior and may interrupt in-flight work.

The implementation does not forcibly terminate handlers that ignore context
cancellation. In that case the worker remains alive until the handler and its
lease-renewal operations stop, preventing database cleanup from racing with
active work.
